## 결정 1 — 학사(Academic) 정보를 제품 범위에 넣을 것인가

### 1.1 확인된 제약

| 제약 | 출처 | 결정에 미치는 영향 |
|---|---|---|
| Essentials는 **행정** 체크리스트로 정의됨 | `DEC-040` §7 | 학사를 여기 넣으면 정의 확장 = 새 DEC 필요 |
| 행정 완료는 문화 집계에 **절대** 기여 못 함 | CLAUDE.md MUST 8 | 학사를 Culture에 넣으면 병풍이 열린다 |
| 병풍 계약은 `total > 0 && total <= 48 && total % 6 === 0` | `completions.test.ts:50` | **카탈로그 크기와 무관.** 미션 추가가 계약을 깨지 않는다 |
| `MISSIONS.length`는 `toBeGreaterThan(0)`만 검사 | `missions.test.ts:5` | 55개는 **테스트로 잠겨 있지 않다.** 미션 추가는 기계적으로 싸다 |
| 학사일정은 매 학기 변경, 대학별 상이 | §11.0 필터 2 | 정적 로컬 앱이 소유하기 **최악의 데이터 유형** |

> 핵심: **기술적으로는 싸고, 의미론적으로 비싸다.** 미션을 늘리는 건 테스트도 안 깨고 병풍 수식도 안 깬다. 문제는 "수강신청 완료가 병풍 한 폭을 여는 게 맞는가"와 "학기마다 썩는 날짜를 앱이 소유할 것인가"다.

### 1.2 선택지

#### 안 A — 넣지 않는다 (현상 유지)

- **하는 일**: 없음. 학사는 대학 소관으로 남긴다.
- **비용**: 0
- **얻는 것**: 범위 규율. `DEC-040`의 Essentials=행정 정의가 깨끗하게 유지된다. 콘텐츠 검증 원장이 안 늘어난다 (§9 P0가 아직 미완인 상태에서 이건 실질 이득이다).
- **잃는 것**: PRD §3.2 "내 조건에서 지금 해야 하는 일"의 실제 큰 덩어리를 계속 비워둔다. 앱이 떡볶이는 안내하고 수강신청은 안 한다는 상태가 지속된다.
- **필요한 결정 문서**: 없음
- **되돌릴 조건**: 워크스루에서 학사 누락이 반복 지적되면 재검토

#### 안 B — 링크 온리 (More 탭 참조 화면) ★ 권장

- **하는 일**: 9개 대학의 **학사일정·수강신청 공식 페이지 링크 9건**과 한국 대학 학사 구조의 **공통 개요**(성적 체계, 수강신청 방식, 학점 인정 절차의 존재)만 넣는다. **날짜는 앱에 넣지 않는다.**
- **비용**: 낮음. 링크 9건 + 개요 텍스트 1화면. 기존 `University` 레코드에 필드 하나 추가.
- **얻는 것**: 사용자가 "어디서 찾아야 하는지"를 얻는다 — 이게 실제 미충족 욕구의 대부분이다. **MUST 12(실행 가능 링크 + 신선도 + 최종 권위)를 그대로 만족**하고, 썩는 데이터를 소유하지 않는다. `DEC-040` 정의를 건드리지 않는다 (More는 "보조 정보" 탭이라 PRD §4에 이미 부합).
- **잃는 것**: "지금 무엇을 해야 하는가"의 타이밍 안내는 못 준다. 수강신청 경쟁 같은 시점 압박은 여전히 사용자 몫.
- **필요한 결정 문서**: 없음 또는 경량 기록. **`DEC-040` 개정 불필요** — 이게 B의 가장 큰 장점이다.
- **되돌릴 조건**: 링크 클릭률이 무의미하거나, 사용자가 여전히 타이밍을 놓친다는 증거가 나오면 D로 승격

#### 안 C — Culture의 `settle` 카테고리로 흡수

- **하는 일**: "수강신청 마치기", "학사일정 확인하기" 등을 문화 미션으로 추가.
- **비용**: 낮음 (테스트가 안 잠겨 있음)
- **얻는 것**: 구현이 가장 빠르다.
- **잃는 것**: **병풍 집계 오염.** 학사는 행정에 가까운데 완료가 병풍을 연다. MUST 8의 취지(행정 완료는 예술 보상과 분리)를 우회하는 결과가 된다. `DEC-040` §7이 문화 완료만 48회 집계에 넣도록 명시한 것과 정면으로 충돌.
- **판정**: **기각 권장.** 싸다는 이유로 제품의 상태 모델을 흐린다.

#### 안 D — Essentials에 학사 스테이지 신설

- **하는 일**: 조건부 태스크로 정식 편입. `universityId` 축으로 대학별 분기, `programStartDate` 기반 타이밍.
- **비용**: 높음. 9개 대학 × 학사일정을 **매 학기 갱신**해야 하고, `volatility: high` 데이터를 앱이 소유하게 된다. §9 P0/P1이 미완인 상태에서 원장이 크게 늘어난다.
- **얻는 것**: PRD §3.2를 온전히 충족. 타이밍 안내까지 가능.
- **잃는 것**: 운영 부담. `DEC-040` 되돌릴 조건 ④ "문화 콘텐츠 유지·검증 비용을 감당할 운영 주체가 없음"이 이미 리스크로 기록돼 있는데, 여기에 학사 원장을 더한다.
- **필요한 결정 문서**: **`DEC-041` 필수** — Essentials 정의 확장
- **되돌릴 조건**: 한 학기 갱신을 못 지키면 즉시 B로 축소

### 1.3 권장

**B → (측정 후) D.** 지금은 B.

이유 셋:
1. 미충족 욕구의 대부분은 "정보"가 아니라 "어디서 찾는지"다. B가 그걸 준다.
2. 학사일정은 §11.0 필터 2(썩지 않는가)를 통과하지 못한다. 앱이 소유하면 안 되는 데이터를 링크로 넘기는 게 정확한 처리다.
3. **B는 `DEC-040` 개정 없이 가능하다.** A와 D 사이에서 결정을 미루는 게 아니라, 결정을 싸게 되돌릴 수 있는 상태로 만든다.

C는 기각을 권한다 — 병풍 집계 오염은 되돌리기가 비싸다 (사용자 진행도에 이미 반영된 뒤에는 소급 정정이 불가능).

## 결정 2 — v1 온보딩 잔재(`profile.tsx` / `sign-in.tsx` / `stayType`)

### 2.1 확인된 사실 — 이전 서술 정정

`CONTENT_INVENTORY.md` §11.3은 "앱이 D-4·H-1 사용자를 받아놓고 콘텐츠가 0건"이라고 적었다. **이 전제는 틀렸다.** 해당 화면은 도달 불가능하다.

| 확인 | 근거 |
|---|---|
| `ONBOARDING_ROUTES`에 `profile`·`sign-in` **없음** (7개: university→program→housing→stay-length→nationality→dates→era) | `src/lib/storage.ts:27` |
| 온보딩 **미완료** 시 `profile`·`sign-in` 진입은 리다이렉트 | `app/_layout.tsx:190` |
| 온보딩 **완료** 시에도 `era` 외 온보딩 경로는 탭으로 리다이렉트 | `app/_layout.tsx:198` |
| `sign-in.tsx`는 `profile`로의 `<Redirect>` 한 줄 (제거된 Auth의 잔재) | `app/(onboarding)/sign-in.tsx:5` |
| `stayType`은 **write-only** — 읽는 곳 0, export 0, migration 0, test 0 | `grep` 전수 |

→ **잘못된 안내가 사용자에게 나가는 버그는 없다.** 실제 문제는 두 가지로 축소된다:
1. 웹에서 `/(onboarding)/profile` 직접 URL이 살아 있어, 가드가 작동하기 전 **v1 화면이 순간 렌더**된다 (MUST 16 맥락에서 웹은 직접 URL을 보존하므로).
2. **데드 코드가 감사를 오염시킨다.** 실제로 이번 인벤토리 작업에서 이 코드 때문에 잘못된 결론을 한 번 냈다. 이건 가설이 아니라 관찰된 비용이다.

### 2.2 선택지

#### 안 A — 삭제 ★ 권장

- **하는 일**: `app/(onboarding)/profile.tsx`, `app/(onboarding)/sign-in.tsx`, `_layout.tsx`의 두 `Stack.Screen`, `app/_layout.tsx:190`의 특례 분기, `UserProfile.stayType` 필드를 제거.
- **비용**: 거의 0. 읽는 코드가 없고, export·migration·test에 걸리지 않는다. `displayName`이 profile.tsx에서만 수집된다면 그 처리만 확인 필요.
- **얻는 것**: 직접 URL로 v1 UI가 노출되는 경로 제거. 가드 코드 단순화. 이후 감사에서 오탐 제거.
- **잃는 것**: 없음. `stayType`에 저장된 기존 사용자 값이 있다면 버려지지만, **읽는 곳이 없으므로 기능 손실이 없다.**
- **주의**: MMKV에 이미 `stayType`이 든 프로필이 있는 기기에서 타입 제거 시 파싱 오류가 나지 않는지 `storageMigrations.ts` 경로로 확인. (필드 삭제는 보통 무해하지만 확인은 필요.)

#### 안 B — `stayType` 필드만 제거, 화면은 유지

- **하는 일**: 타입과 저장만 정리하고 화면 파일은 남긴다.
- **얻는 것**: 삭제 범위 최소화.
- **잃는 것**: 직접 URL 노출과 감사 오염이 그대로 남는다. **문제의 원인이 아니라 증상만 건드린다.**
- **판정**: 비권장

#### 안 C — 유지 + 데드 코드임을 문서화

- **하는 일**: 코드 상단에 "v1 잔재, 도달 불가" 주석 + `CONTENT_INVENTORY`에 기록.
- **얻는 것**: 0 리스크
- **잃는 것**: 웹 직접 URL 노출 유지. 데드 코드 보존 비용이 계속 누적.
- **판정**: 삭제가 위험하다고 판명될 때만

### 2.3 별개 질문 — D-4(어학연수) / H-1(워킹홀리데이) 지원 여부

이건 **결정 2가 아니라 결정 1과 같은 성격의 범위 질문**이고, 현재 버그가 아니므로 급하지 않다.

- PRD §3.1의 1차 사용자는 **교환학생**이다.
- 지원하려면 체류자격별 조건 분기를 실제로 만들어야 한다 (비자 요건, 취업 가능 범위, 보험 적용이 전부 다름). §11.1①의 시간제취업 주제와 직결된다.
- **권장**: 현재 범위에서 제외를 명시. 안 A로 선택지를 지우면 범위가 코드와 문서에서 일치한다.

### 2.4 권장

**안 A (삭제) + D-4/H-1은 범위 밖으로 명시.**

`DEC-042`로 기록할 만한 내용은 크지 않다 — "제거된 Auth의 잔재 화면과 미사용 필드를 삭제하고, 지원 체류자격을 교환·방문 학생으로 명시한다" 한 줄이면 된다.

## 두 결정의 관계

독립적이므로 **따로 결정해도 된다.** 다만 순서는 결정 2가 먼저인 게 낫다:

- 결정 2는 비용이 0에 가깝고 되돌릴 필요가 없다.
- 결정 1(특히 안 D)은 온보딩 축을 건드릴 가능성이 있는데, 그때 v1 잔재가 남아 있으면 판단이 다시 오염된다.

| | 권장안 | 비용 | DEC 필요 | 되돌리기 |
|---|---|---|---|---|
| 결정 2 | A — 삭제 | ~0 | 경량 (`DEC-042`) | 불필요 |
| 결정 1 | B — 링크 온리 | 낮음 | **불필요** | 쉬움 (D로 승격) |

두 안 모두 **`DEC-040`을 개정하지 않고** 진행 가능하다. 이게 지금 시점(§9 P0 미완, 측정 데이터 0)에서 가장 중요한 속성이라고 판단한다.
